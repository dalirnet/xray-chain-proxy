# پیشرفته

## معماری‌های چند EDGE

### EDGE های موازی

چند نقطه ورود به یک GATEWAY.

کاربردها:

- توزیع بار
- تنوع جغرافیایی
- افزونگی

راه‌اندازی: روی هر سرور `setup edge` را اجرا کنید و همه را به SSH همان GATEWAY وصل کنید.

### EDGE های زنجیره‌ای

چند هاپ برای حریم خصوصی بیشتر.

```
Client --> EDGE 1 ==ssh==> EDGE 2 ==ssh==> GATEWAY --> Internet
```

کاربردها:

- لایه‌های ناشناسی اضافی
- دور زدن بازرسی عمیق بسته‌ها

راه‌اندازی:

1. GATEWAY را عادی راه‌اندازی کنید
2. EDGE 2 را به SSH سرور GATEWAY وصل کنید
3. EDGE 1 را به SSH سرور EDGE 2 وصل کنید

برای اینکه EDGE 2 بتواند لینک بپذیرد، اول کاربر تونل را روی آن بسازید و بعد آن را به GATEWAY وصل کنید:

```bash
./xcp.sh setup gateway   # روی EDGE 2؛ کاربر xcp و قانون sshd را می‌سازد
./xcp.sh setup edge      # سپس EDGE 2 را به GATEWAY وصل می‌کند
```

دستور دوم کانفیگ را به شکل EDGE بازنویسی می‌کند و کاربر SSH باقی می‌ماند، پس EDGE 1 می‌تواند به آن وصل شود.

روی یک EDGE میانی، پورت `127.0.0.1:10080` متعلق به `ssh -L` خود آن سرور است. تونلی که از EDGE 1 می‌رسد به همان پورت می‌نشیند و روی تونل EDGE 2 ادامه پیدا می‌کند، پس ترافیک از دو هاپ SSH عبور می‌کند و از Xray سرور GATEWAY خارج می‌شود:

```
EDGE 1 (Xray) ==ssh==> EDGE 2 (ssh -L) ==ssh==> GATEWAY (Xray) --> Internet
```

قوانین مسیریابی و آمار هر کاربر روی همان EDGE که کلاینت به آن وصل می‌شود و روی GATEWAY اعمال می‌شوند. EDGE میانی فقط بایت‌ها را عبور می‌دهد.

## پایداری لینک

مسیر EDGE به GATEWAY از یک لینک بین‌المللی عبور می‌کند؛ جایی که تاخیر، از دست رفتن بسته و شکل‌دهی ترافیک وجود دارد. چهار چیز آن را سرپا نگه می‌دارد.

### کنترل ازدحام

راه‌اندازی فایل `/etc/sysctl.d/99-xcp.conf` را روی هر دو سرور می‌نویسد:

```
net.core.default_qdisc = fq
net.ipv4.tcp_congestion_control = bbr
net.core.rmem_max = 16777216
net.core.wmem_max = 16777216
net.ipv4.tcp_rmem = 4096 87380 16777216
net.ipv4.tcp_wmem = 4096 65536 16777216
net.ipv4.tcp_mtu_probing = 1
net.ipv4.tcp_slow_start_after_idle = 0
```

الگوریتم پیش‌فرض `cubic` هر بسته گم‌شده را نشانه ازدحام می‌گیرد و عقب می‌کشد؛ روی یک مسیر شکل‌داده‌شده بیشتر وقتش را صرف همین عقب کشیدن می‌کند. BBR بر اساس پهنای باند اندازه‌گیری‌شده و زمان رفت‌وبرگشت تنظیم می‌کند، پس لینک را پر نگه می‌دارد. بافرهای ۱۶ مگابایتی به یک اتصال با تاخیر بالا اجازه می‌دهند به اندازه حاصل‌ضرب پهنای باند در تاخیر داده در مسیر داشته باشد؛ مقداری که پیش‌فرض‌ها روی مسیر ۱۵۰ میلی‌ثانیه به بالا خیلی پایین‌تر محدود می‌کنند.

کرنلی که BBR داشته باشد آن را می‌گیرد؛ بقیه کنترل ازدحام فعلی خود را نگه می‌دارند و راه‌اندازی گزارش می‌دهد کدام اعمال شد.

### بررسی سلامت

`ServerAliveInterval` فقط زنده بودن سوکت را ثابت می‌کند. یک لینک شکل‌داده‌شده به keepalive پاسخ می‌دهد در حالی که توان عبورش فروریخته است، بنابراین `xray-tunnel-health.timer` هر ۶۰ ثانیه یک صفحه را از داخل تونل می‌گیرد:

```bash
./xcp.sh link health     # اجرای دستی یک بررسی
```

دو شکست پشت سر هم، تونل و Xray پشت آن را ری‌استارت می‌کند. یک درخواست کند به عنوان نویز شمرده می‌شود و با موفقیت بعدی پاک می‌شود.

### سیاست ری‌استارت

یونیت `xray-tunnel` مقدار `StartLimitIntervalSec=0` را تنظیم می‌کند تا systemd برای همیشه تلاش را ادامه دهد. با محدودیت پیش‌فرض (۵ بار اجرا در ۱۰ ثانیه)، یک GATEWAY که هنگام بوت لحظه‌ای در دسترس نباشد — `ssh` روی اتصال رد شده یا خطای DNS بلافاصله خارج می‌شود — یونیت را در وضعیت failed رها می‌کرد که خودبه‌خود برنمی‌گردد.

### تنظیمات انتقال

دستور `ssh` با `IPQoS=none` اجرا می‌شود و فیلد DSCP را دست‌نخورده می‌گذارد. OpenSSH در حالت عادی بسته‌ها را `af21` یا `cs1` علامت می‌زند که هم یک امضای مشخص است و هم می‌تواند تونل را در صف با شکل‌دهی متفاوت قرار دهد. رمزنگاری روی CPUهای دارای دستورات AES به `aes128-gcm@openssh.com` و در بقیه موارد به `chacha20-poly1305@openssh.com` ثابت می‌شود.

### خواندن کیفیت لینک

```bash
./xcp.sh status
```

```
Tunnel: ● Running
  RTT/jitter:  47.3/2.1 ms
  Retrans:     0/1841
Health: ● Checking every 60s
```

عدد اول زمان رفت‌وبرگشت و عدد دوم واریانس آن است؛ جیتر بیشتر از حدود ۲۰ درصد RTT همان چیزی است که کار کردن با سشن را کند نشان می‌دهد. `Retrans` تعداد بسته‌هایی است که کرنل مجبور شده دوباره بفرستد؛ رشد این عدد در حالت بیکار، اولین نشانه یک مسیر شکل‌داده‌شده است، خیلی قبل از اینکه به شکل کندی خودش را نشان دهد.

## جزئیات تونل SSH

| مورد        | مقدار                                                           |
| ----------- | --------------------------------------------------------------- |
| سرویس       | `xray-tunnel.service` (systemd با ری‌استارت خودکار)             |
| ورود        | `sshpass -f /usr/local/xray/tunnel_pass` (دسترسی 600)           |
| known hosts | `/usr/local/xray/known_hosts`                                   |
| فوروارد     | `-L 127.0.0.1:10080:127.0.0.1:10080`                            |
| سر محلی     | `127.0.0.1:10080` که خروجی `proxy` در Xray از آن استفاده می‌کند |
| سر مقابل    | `127.0.0.1:10080` یعنی اینباند `tunnel-in`                      |

خواندن رمز از فایل باعث می‌شود رمز در `ps` و فایل سرویس دیده نشود.

مقادیر keepalive، انتخاب رمزنگاری و سیاست ری‌استارت در بخش [پایداری لینک](#پایداری-لینک) توضیح داده شده‌اند.

### کاربر تونل

راه‌اندازی GATEWAY کاربر `xcp` را با شل `/usr/sbin/nologin` می‌سازد و این بلوک را به `/etc/ssh/sshd_config` اضافه می‌کند:

```
Match User xcp
    PasswordAuthentication yes
    AllowTcpForwarding yes
    PermitOpen 127.0.0.1:10080
    PermitTTY no
    X11Forwarding no
```

بلوک `Match` تنظیمات را فقط برای همین کاربر جایگزین می‌کند، پس سروری که `PasswordAuthentication no` دارد آن را برای بقیه نگه می‌دارد. `PermitOpen` این حساب را به همان یک فوروارد زنجیره محدود می‌کند. کانفیگ با `sshd -t` بررسی می‌شود و اگر تست رد شود به حالت قبل برمی‌گردد.

### TCP روی TCP

SSH خودش TCP است و بیشتر ترافیک تونل هم TCP، پس یک بسته گم‌شده روی اتصال بیرونی باعث عقب‌نشینی اتصال درونی هم می‌شود. راه‌اندازی این را از قبل جبران می‌کند: BBR و بافرهای بزرگ‌تر در `/etc/sysctl.d/99-xcp.conf` نوشته می‌شوند. بخش [کنترل ازدحام](#کنترل-ازدحام) توضیح می‌دهد چه چیزی تنظیم می‌شود و چرا.

### UDP

پورت‌فورواردینگ SSH ترافیک TCP را عبور می‌دهد. کانفیگ EDGE این را مدیریت می‌کند:

- DNS کلاینت‌ها روی UDP/53 با خروجی `dns-out` و از طریق TCP در داخل زنجیره پاسخ داده می‌شود
- بقیه ترافیک UDP به `blocked` می‌رود؛ QUIC و پروتکل‌های مشابه خودکار به TCP برمی‌گردند

## DNS

هر دو نوع سرور روی `127.0.0.1:53` (TCP و UDP) ریزالور دارند که از سه بخش ساخته می‌شود:

| بخش              | نقش                                                      |
| ---------------- | -------------------------------------------------------- |
| اینباند `dns-in` | `dokodemo-door` روی پورت ۵۳ که به ریزالور هدایت می‌کند   |
| `dns-out`        | خروجی `dns` در Xray که از کلاینت داخلی پاسخ می‌دهد       |
| `.dns.servers`   | خود ریزالور که با کلید `.xcp.dns` در کانفیگ ذخیره می‌شود |

`dns-in` به‌طور پیش‌فرض روی ۵۳ گوش می‌دهد؛ `config port` آن را به هر پورتی می‌برد و ریزالوری که درخواست‌ها به آن می‌رسند روی ۵۳ می‌ماند. پورت دلخواه از ابتدا با `systemd-resolved` تداخلی ندارد، پس واگذاری stub که در ادامه آمده فقط مربوط به ۵۳ است.

روی EDGE ریزالور به شکل `tcp://ADDRESS` نوشته می‌شود تا از تونل عبور کند. آدرس DoH همان‌طور که وارد شده ذخیره می‌شود و روی HTTPS از داخل زنجیره می‌گذرد.

```bash
./xcp.sh config set
# انتخاب: 3) dns
```

ترافیکی که از VLESS یا Shadowsocks می‌رسد به صورت خودکار از همین مسیر ریزالو می‌شود، پس کلاینت‌ها با هر DNS که دارند کار می‌کنند.

پیش‌فرض روی لوکال است، چون ریزالوری که از اینترنت در دسترس باشد توسط اسکنرها پیدا و برای حملات تقویتی استفاده می‌شود؛ همین یکی از دلایل رایج تعلیق حساب توسط ارائه‌دهنده است. برای اینکه یک دستگاه بتواند مستقیم از آن پرس‌وجو کند، آن دستگاه را با آدرس مجاز کنید — بخش [دسترسی DNS](commands.md#دسترسی-dns) را ببینید:

```bash
./xcp.sh dns add 203.0.113.9
```

### systemd-resolved

اوبونتو یک ریزالور stub روی `127.0.0.53:53` اجرا می‌کند. این آدرس با `127.0.0.1:53` که Xray می‌گیرد فرق دارد، پس این دو معمولا در کنار هم کار می‌کنند و راه‌اندازی کاری با stub ندارد.

بعضی ایمیج‌ها ریزالوری روی خود `127.0.0.1:53` می‌گذارند — مثلا dnsmasq در NetworkManager. تنها در همین حالت راه‌اندازی پورت را تحویل می‌گیرد: مقدار `DNSStubListener=no` را در `/etc/systemd/resolved.conf.d/xcp.conf` می‌نویسد، `systemd-resolved` را ری‌استارت می‌کند و `/etc/resolv.conf` را به `/run/systemd/resolve/resolv.conf` لینک می‌کند تا سرور به ریزالو کردن ادامه دهد. دستور `uninstall` ریزالور stub را برمی‌گرداند.

## فایروال

اسکریپت در صورت فعال بودن UFW، پورت‌ها را باز می‌کند. برای فایروال‌های دیگر و برای security group ارائه‌دهنده، هر دو نقش به قوانین یکسان نیاز دارند:

```
22, 80, 443, 8443/tcp
8443/udp
```

هر دو نقش VLESS+REALITY (443)، Shadowsocks (8443) یا هر دو را، طبق انتخاب هنگام راه‌اندازی، سرویس می‌دهند — فقط پورت پروتکل‌های فعال را باز کنید. سرور GATEWAY علاوه بر این، تونل را روی SSH (22) می‌پذیرد.

| پورت   | پروتکل‌ها | دلیل                                                       |
| ------ | --------- | ---------------------------------------------------------- |
| `22`   | TCP       | SSH                                                        |
| `80`   | TCP       | پاسخ‌دهنده آی‌پی یک سوکت `ListenStream` است                |
| `443`  | TCP       | REALITY مقدار `streamSettings.network` را `tcp` می‌گذارد   |
| `8443` | TCP + UDP | Shadowsocks مقدار `settings.network` را `tcp,udp` می‌گذارد |

از میان پروتکل‌های کلاینت تنها Shadowsocks ترافیک UDP را حمل می‌کند، پس تنها همان به قانون UDP نیاز دارد. توجه کنید که بسته UDP رسیده به **EDGE** در هر صورت توسط قانون انتهایی مسیریابی دور ریخته می‌شود، چون تونل SSH فقط TCP حمل می‌کند — ترافیک UDP روی Shadowsocks تنها از یک **GATEWAY** به اینترنت می‌رسد.

پورت‌های بالا پیش‌فرض هستند. با پورت‌های دلخواه از راه‌اندازی یا `config port`، همان‌ها را باز کنید — `ufw` آن‌ها را خودکار می‌گیرد.

پورت `53` به هر دو پروتکل نیاز دارد، ولی فقط از سمت کلاینت‌هایی که با `dns add` مجاز می‌کنید، پس به جای یک قانون فراگیر، قانون مخصوص همان مبدا می‌گیرد. پورت‌های `10080`، `10085` و `11080` روی `127.0.0.1` می‌مانند و اصلا به قانون نیاز ندارند.

## REALITY

ورودی VLESS روی ۴۴۳ دست‌دادن TLS یک سایت واقعی را قرض می‌گیرد. دست‌دادن‌های کلاینت‌های ناشناس به `dest` منتقل می‌شوند، پس یک پروب فعال یک پاسخ واقعی TLS 1.3 با زنجیره گواهی معتبر همان سایت می‌گیرد — یک گواهی واقعی که یک سایت واقعی ارائه می‌کند.

### نیازی به دامنه نیست

دو نام در کار است و فقط یکی از آن‌ها به شما مربوط می‌شود — هیچ‌کدام به رکورد DNS به سمت سرور شما نیاز ندارند:

- `dest` / `sni` دامنه **شخص دیگری** است. شما دست‌دادن آن را قرض می‌گیرید، پس گواهی در مسئولیت همان سایت می‌ماند.
- سرور شما با **آی‌پی خام** در دسترس است و همان چیزی است که در لینک اشتراک قرار می‌گیرد.

```
vless://<uuid>@203.0.113.9:443?...&sni=www.cloudflare.com&...
              ↑ آی‌پی شما            ↑ دامنه قرض‌گرفته‌شده
```

کلاینت یک اتصال TCP به آی‌پی شما باز می‌کند و بعد یک ClientHello با نام قرض‌گرفته‌شده می‌فرستد. پروتکل‌های VLESS+TLS معمولی و Trojan به دامنه‌ای که مالکش باشید، یک رکورد DNS و یک گواهی نگهداری‌شده نیاز دارند. REALITY از یک آی‌پی خام کار می‌کند. قرار دادن یک دامنه جلوی سرور هم کار می‌کند و تعویض آی‌پی را ساده‌تر می‌کند.

راه‌اندازی جفت‌کلید x25519 را با `xray x25519` و یک `shortId` تصادفی ۸ بایتی می‌سازد. کلید خصوصی در ورودی می‌ماند و نیمه عمومی در بخش `xcp.reality` کانفیگ ذخیره می‌شود؛ همان چیزی که بعدا لینک‌های اشتراک را بازمی‌سازد.

### انتخاب dest

راه‌اندازی دامنه را با `openssl s_client` بررسی می‌کند و وقتی با TLS 1.3 و HTTP/2 پاسخ دهد آن را می‌پذیرد. یک `dest` خوب:

- از TLS 1.3 و HTTP/2 پشتیبانی می‌کند
- از GATEWAY قابل دسترسی است
- در منطقه‌ای که کلاینت‌ها از آن وصل می‌شوند فیلتر نیست — یک دامنه مسدود، یک دست‌دادن خراب تحویل پروب‌ها می‌دهد
- متعلق به شخص دیگری است و ترجیحا نزدیک سرور قرار دارد

بررسی دستی یک گزینه:

```bash
openssl s_client -connect www.cloudflare.com:443 -tls1_3 -alpn h2 </dev/null 2>&1 \
  | grep -E 'Protocol|ALPN'
```

### دقت ساعت

احراز هویت REALITY بر پایه زمان است. بیش از حدود ۹۰ ثانیه اختلاف بین کلاینت و سرور، احراز هویت را با خطایی که به ساعت اشاره نمی‌کند شکست می‌دهد. `chrony` را نصب یا `systemd-timesyncd` را فعال کنید.

### UDP

پروتکل VLESS ترافیک UDP را داخل اتصال TCP خود حمل می‌کند، پس QUIC، تماس‌ها و بازی‌ها برای کلاینت‌هایی که مستقیم به **GATEWAY** وصل می‌شوند کار می‌کنند. روی **EDGE** این ترافیک همچنان به قانون مسیریابی مسدودکننده UDP می‌رسد، چون تونل SSH به گیت‌وی فقط TCP حمل می‌کند.

## پورت ۸۰

هر دو نقش روی ۸۰ (یا پورتی که هنگام راه‌اندازی یا با `config port` انتخاب شده) با آدرسی که اتصال از آن می‌رسد پاسخ می‌دهند:

```bash
curl http://SERVER_IP     # 203.0.113.9
```

یونیت `xcp-web.socket` این پورت را در اختیار دارد و هر اتصال را به یک پاسخ‌دهنده کوتاه‌عمر با کاربر `nobody` و تنظیمات `ProtectSystem=strict` و `NoNewPrivileges` می‌سپارد. systemd سوکت را در اختیار دارد و هر پاسخ‌دهنده با پایان اتصال خودش خارج می‌شود. اگر چیز دیگری این پورت را گرفته باشد، راه‌اندازی آن را گزارش می‌کند و از پاسخ‌دهنده می‌گذرد. با انتخاب پورت دیگری در `config port` پاسخ‌دهنده برمی‌گردد؛ پورت در `.xcp.web_port` ذخیره می‌شود.

## عیب‌یابی

### Xray شروع نمی‌شود

بررسی تنظیمات:

```bash
/usr/local/xray/xray run -test -config /usr/local/xray/config.json
```

بررسی لاگ systemd:

```bash
journalctl -u xray -n 50
```

### اتصال رد شد

1. بررسی وضعیت: `./xcp.sh status`
2. بررسی فایروال: `ufw status`
3. بررسی پورت‌ها: `ss -tlnp | grep xray`

### EDGE به GATEWAY وصل نمی‌شود

1. بررسی تونل: `./xcp.sh link ls`
2. مشاهده لاگ تونل: `./xcp.sh link logs`
3. تست دستی SSH:
    ```bash
    ssh -p 22 xcp@GATEWAY_IP
    ```
    کاربر `xcp` فقط اجازه فوروارد دارد، پس ورود موفق بلافاصله بسته می‌شود؛ همین نتیجه درست است.
4. مطمئن شوید `sshd` سرور GATEWAY اجراست و فایروال پورت SSH را باز گذاشته
5. ری‌استارت تونل: `./xcp.sh link restart`

### پیام «هیچ پروکسی پشت تونل نیست»

یعنی ورود SSH انجام شده ولی سر مقابل روی `127.0.0.1:10080` پاسخی نداده. روی آن سرور `./xcp.sh setup gateway` را اجرا کنید، با `./xcp.sh status` از بالا بودن Xray مطمئن شوید و بعد روی EDGE دوباره `./xcp.sh link set` را بزنید.

### ورود با رمز رد می‌شود

روی GATEWAY بررسی کنید کاربر تونل و بلوک sshd آن باقی مانده باشند:

```bash
id xcp
sshd -T -C user=xcp | grep -E 'passwordauthentication|permitopen'
```

انتظار: `passwordauthentication yes` و `permitopen 127.0.0.1:10080`. برای بازگرداندن آن‌ها و ساخت رمز تازه، `./xcp.sh setup gateway` را دوباره اجرا کنید.

### تونل مدام ری‌استارت می‌شود

معمولاً به خاطر `ExitOnForwardFailure` است: یا پورت محلی اشغال است یا sshd فورواردینگ را رد می‌کند.

```bash
journalctl -u xray-tunnel -n 50
ss -tlnp | grep 10080                   # پورت محلی اشغال است؟
```

روی GATEWAY در `/etc/ssh/sshd_config` بررسی کنید:

```
AllowTcpForwarding yes
```

### کلاینت‌های VLESS وصل نمی‌شوند

سرور سالم است، پورت باز است و کلاینت‌ها باز هم وصل نمی‌شوند — معمولا شبیه اشتباه بودن اعتبارنامه به نظر می‌رسد. اولین چیزی که باید بررسی کنید dest است.

پروتکل REALITY دست‌دادن dest را قرض می‌گیرد و به کلاینت می‌دهد. یک دامنه می‌تواند با TLS 1.3 و HTTP/2 پاسخ دهد و باز هم helloیی برگرداند که REALITY نتواند از آن استفاده کند؛ در این حالت هر کلاینت پیش از خوانده شدن uuid انداخته می‌شود. چیزی در لاگ سرور نگران‌کننده به نظر نمی‌رسد و کلاینت فقط پایان اتصال را می‌بیند.

```bash
./xcp.sh test          # گزارش می‌کند که آیا کلاینت دست‌دادن را کامل می‌کند
```

شکست در آنجا نام dest را می‌آورد. آن را عوض و دوباره تست کنید:

```bash
./xcp.sh config dest   # گزینه‌ها: www.cloudflare.com، dl.google.com، cdn.jsdelivr.net، www.speedtest.net
./xcp.sh user ls       # مقدار SNI عوض شده، پس لینک‌ها را دوباره وارد کنید
```

دو نکته دیگر که همین‌جا ارزش بررسی دارند: لینک اشتراک باید با کلیدهای فعلی بخواند، چون هر بار `setup` کلید تازه می‌سازد؛ و ساعت هر دو طرف باید دقیق باشد، چون احراز هویت REALITY بر پایه زمان است و حدود ۹۰ ثانیه اختلاف مرز آن است.

### DNS پاسخ نمی‌دهد

ریزالور روی لوکال پاسخ می‌دهد، پس از خود سرور تستش کنید:

```bash
dig @127.0.0.1 example.com
ss -ulnp | grep :53
```

انتظار داریم `xray` را روی `127.0.0.1:53` ببینید. اگر چیز دیگری پورت را گرفته، مرحله [systemd-resolved](#systemd-resolved) را دستی انجام دهید.

برای پرس‌وجو از یک ماشین دیگر، آن ماشین باید اول مجاز شده باشد و `ufw` هم فعال باشد تا فهرست را اعمال کند:

```bash
./xcp.sh dns ls                 # چه کسی مجاز است و آیا اعمال می‌شود
./xcp.sh dns add 203.0.113.9
```
